# Gemini 連携の調査まとめ (#11)

2026-11-17 時点。Gemini (Web, `@Notion`) から本サーバーの MCP ツールを呼ぶ際の不具合の調査記録。

## 症状

- 「常に許可」を設定していても許可を求められる
- 「Notion に接続しています」の表示のまま止まる (20〜30 秒)
- 「エラーが発生しました (1)」(コードの説明はヘルプにもない)
- ツールが成功しているのに Gemini が「Notion のツールが使えない」と回答する

## 調査方法

Chrome を操作して Gemini から `@Notion 「Core Memory」を検索して…` を繰り返し送り、
Firestore の `events` (後述の追加項目つき) と Cloud Run ログを突き合わせた。
events には `rpc_method` / `tool_name` / `duration_ms` / `result_bytes` / `tool_error` / `req_info` (ヘッダ要約) を追加した
(トークン・引数・応答本文は記録しない)。確認コマンドは `docs/runbook.md` §5。

## 実施した修正

| PR | 内容 |
|---|---|
| #13 | Notion API のタイムアウト (10 秒) と 429/5xx リトライ |
| #14 | `/mcp` の 500 を JSON-RPC 形式に、401 に `error="invalid_token"` |
| #15 | events 書き込みの待ち時間に上限 (1.5 秒) |
| #16 | ブロック子要素の並列取得 (同時 3・総 200 呼び出し上限) |
| #17 | レート制限の IP 判定を `X-Forwarded-For` の末尾に |
| #18, #19, #21 | events に RPC メソッド・結果サイズ・エラー・ヘッダ要約を記録 |

## 確定したこと (サーバー側は健全)

- サーバーの応答は常に 200/202 で、処理時間は 20〜600 ms (Notion API 呼び出しを含む `tools/call` で 300〜1400 ms)
- トークン更新 (`refresh_token`) は正常に動き、再認可や 401 は発生していない
- ツールの失敗 (`tool_error`) は一度も記録されていない。検索結果は 1〜2 件 (350〜610 バイト) を正しく返している
- 応答は仕様どおりの JSON-RPC。`tools/list` のスキーマにも異常はない
- 常時 1 インスタンスにしなくても (コールドスタートの有無に関係なく) 再現する

## Gemini 側の挙動 (観察)

- ヘッダは常に `Mcp-Protocol-Version: 2025-11-25`、UA は `Google`
- 同じリクエストを 2〜3 本並列で送る (`initialize`、`tools/call` とも)
- 毎回 `GET /mcp` (SSE 用) を試し、405 を受ける
- 多くの回で、まず `initialize` なしの `tools/list` を単独で送る
  - その後 10〜19 秒空けて `initialize` → `tools/call` に進む回 (成功) と、何も続かず Gemini が「使えない」と回答する回 (失敗) がある
  - 成功・失敗は同じ入力・同じサーバー状態でも入れ替わる
- 接続失敗の約 20 秒後に `GET /revoke` (404) が届くことがある

## 検証した仮説 (実験用スイッチ、すべて既定オフ・本番は元に戻し済み)

| 実験 | スイッチ | 結果 (`tools/call` が届いた割合) |
|---|---|---|
| 基準 (変更なし) | - | 約 2〜3 / 9 |
| POST 応答を SSE (`text/event-stream`) に | `MCP_JSON_RESPONSE=false` (#20) | 0 / 2 (改善せず) |
| `tools/list` から `$schema` / `execution` / `additionalProperties` を除去 | `MCP_SANITIZE_SCHEMA=true` (#22) | 3 / 7 (有意差なし) |
| 署名付き `Mcp-Session-Id` を発行・要求 (欠落は 400) | `MCP_REQUIRE_SESSION=true` (#23) | 2 / 4 (有意差なし) |

セッション実験では、Gemini が 400 を受けて約 0.2 秒で `initialize` に進み、以降のリクエストにセッション ID を付けることを確認した。
標準どおりの挙動は取れるが、成功率の改善にはつながらなかった。サンプルが小さいため、効果が小さい場合は検出できていない可能性がある。

## 結論

- 現状の症状は、サーバー実装の問題としては再現・特定できていない。ツール呼び出しの前後でサーバーは常に成功しており、
  Gemini 側がツールを使うかどうか (または接続処理) の判断で失敗している可能性が高い
- 「許可を求められる」症状は、ツール確認ダイアログか OAuth 認可画面かが未切り分けのまま
  (調査中は refresh が正常に動いていたため、再認可は発生していない)
- 「エラーが発生しました (1)」はサーバーのレスポンスに該当するコードがなく、Gemini 側の汎用エラーと思われる

## 今後の候補

1. Google への報告材料として上記の観察 (特に `initialize` なし `tools/list`、並列重複、成功率のばらつき) を共有する
2. 長期的に使う場合は、失敗時にユーザーが再送すれば通る前提の運用にする (再送で成功する回がある)
3. #8 (events の完全な非同期化) は Cloud Run の CPU 割り当て設定とセットで検討
4. #9 (常時 1 インスタンス) は効果が見込めないため見送り
5. 追加で見るなら、`GET /mcp` に SSE ストリームを返す実験、Gemini の拡張画面の設定・権限表示の確認
